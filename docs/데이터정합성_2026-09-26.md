# 데이터 정합성 복구 — 2026-09-26

유니버스 스냅샷 구멍을 메우러 들어갔다가 **그보다 큰 구멍 세 개**를 같이 찾았다.
그중 하나가 8년 백테스트 결과를 뒤집었다.

> **결론부터.** 트랙 판정이 현재 200종목에만 있어서, 나머지 226종목이 업종
> `"00"`이라는 가짜 그룹 하나에 전부 몰려 서로를 상대로 채점되고 있었다.
> **패널 행의 58%가 여기 해당했다.** 이 프로젝트의 핵심 설계인 2단계 백분위
> (트랙 → 업종)가 절반 이상에서 작동하지 않고 있었다는 뜻이다.
>
> 고치자 **성장주 게이트O 총수익이 +607% → +34%** 가 됐다. 벤치마크는 그대로다
> (+103.2% → +103.6%). 즉 벤치마크 문제가 아니라 전략이 이기지 못한다.

이 문서는 무엇이 어떻게 틀려 있었고, 무엇을 고쳤고, 무엇이 아직 남았는지를 적는다.

## 3. 세 번째 구멍 — 284종목이 트랙 판정 없이 T1이었다

`tracks.parquet`에 현재 200종목만 있었다. 판정이 없는 종목은 `panel.cohort`에서
**기본값 T1(일반)** 으로 처리된다. 은행에 부채비율을 들이대지 않으려고 트랙을
분리한 것인데, 과거 유니버스 종목 284개가 그 분리를 못 받고 있었다.

284개를 판정하니 **68개가 T1이 아니었다.**

| 트랙 | 개수 | 예 |
|---|---|---|
| T3 제약바이오 | 45 | 녹십자 · 보령 · 부광약품 · 신풍제약 · JW중외제약 |
| T2 금융 | 12 | 우리은행 · 메리츠화재 · 메리츠증권 · 서울보증보험 |
| T4 지주 | 11 | 롯데지주 · 하림지주 · 콜마홀딩스 · SK디스커버리 |

`scripts/26_fill_new_tickers.py --what tracks`

### 그런데 트랙보다 업종이 문제였다 — 이것이 결과를 뒤집었다

`grading.build()`는 업종 코드를 `tracks.induty_code`에서 가져온다.
`tracks`에 없는 종목은 `.fillna("00")`으로 처리된다.
**그래서 226종목이 업종 `"00"` 하나에 전부 들어가 있었다.**

`MIN_PEERS = 8`이라 `"00"`은 표본이 충분해 폴백도 걸리지 않았다.
226개 무관한 회사가 하나의 "업종"으로 서로를 상대로 백분위를 받았다.

| | 옛 패널 | 새 패널 |
|---|---|---|
| 총 행 | 38,104 | 38,460 |
| 업종 개수 | 36 | **52** |
| 업종 `"00"` (미판정) | **22,141행 = 58.1%** | **0행** |
| `__TRACK__` 폴백 (업종 표본 8 미만) | 6,872행 | 8,864행 |

업종 코드가 실제로 맞는지 확인했다 — 삼성전자 26(전자부품), 셀트리온 21(의약품),
KB금융 64(금융), 현대차 30(자동차), LG화학 20(화학), 루닛 58(소프트웨어),
서울보증보험 65(보험). 이전에는 포스코엠텍·루닛·서울보증보험이 모두 `"00"`이었다.

원인을 찾는 과정에서 **두 가설을 먼저 세웠다가 버렸다.** 기록해 둘 만하다.

1. *"최신 재무를 가진 종목이 정확히 오늘의 상위 200이라 생존편향이 생겼다"*
   → 옛 패널 상위 5종목 중 신선한 재무 집단 비중 83.0%, 후보 전체 87.5%.
   **오히려 낮다.** 기각.
2. *"트랙이 바뀐 68종목이 결과를 끌어올렸다"*
   → 옛 패널 상위 5종목 384건 중 트랙이 바뀐 종목은 8.6%뿐. 기여가 작다. 기각.

연도별 차이가 2019·2020까지 퍼져 있다는 점이 결정적 단서였다 — 재무 신선도
문제는 2023년 이후만 건드리므로, **모든 해에 영향을 주는 입력**이 따로 있어야 했다.

### 그 과정에서 찾은 오분류

아시아나항공이 **부채비율 1,370%만으로 금융(T2)** 이 됐다. `src/tracks.py`에
"업종코드가 제조인데 부채비율이 금융권 수준이면 코드를 의심한다"는 규칙이 있는데,
항공사는 리스부채 때문에 그 선을 넘는다. 금융으로 보내면 부채비율·유동비율·
영업이익률이 전부 NULL이 되고 은행과 나란히 채점된다.

**금융성 자산이 실제로 재무제표에 있을 때만** 이 규칙이 적용되도록 고쳤다.
484종목 중 이 경로를 탄 것은 아시아나항공과 다우기술 둘뿐이었고, 둘 다 T1로 돌아갔다.

## 4. 고친 뒤의 백테스트 — 결과가 뒤집혔다

`scripts/27_compare_rebuild.py` — 같은 유니버스 조건·같은 거래비용·같은 97개월.

| | 옛 총수익 | 새 총수익 | 변화 | 옛 MDD | 새 MDD |
|---|---|---|---|---|---|
| 유니버스 동일가중 (벤치) | +103.2% | +103.6% | +0.4%p | −35.4% | −35.4% |
| 시총가중 (지수근사) | +255.9% | +243.9% | −12.0%p | −32.8% | −33.2% |
| 가치투자 게이트O | +9.4% | +23.6% | +14.2%p | −68.9% | −53.9% |
| 가치투자 게이트X | +59.7% | +62.0% | +2.3%p | −60.4% | −52.1% |
| **성장주 게이트O** | **+606.6%** | **+34.2%** | **−572.4%p** | −67.2% | −58.4% |
| 성장주 게이트X | +253.0% | +161.8% | −91.2%p | −39.4% | −47.1% |

**벤치마크는 움직이지 않았다.** 그러니 이것은 표본이 바뀐 탓이 아니라,
전략의 선택이 바뀐 탓이다. 매수 종목은 97개월 중 79~99%의 달에서 바뀌었고
평균 5종목 중 2.4~2.5개가 교체됐다.

### 이제 무엇이 남는가

- **유니버스 동일가중(+104%)을 넘은 것은 성장주 게이트X(+162%)뿐**이고 p=0.43으로
  유의하지 않다
- **시총가중 지수(+244%)는 아무 전략도 넘지 못했다**
- 게이트는 양쪽 전략 모두 **끈 쪽이 낫다** (가치 +24%→+62%, 성장 +34%→+162%)
- 단일 부문으로는 **수익성 +470%, 성장성 +347%** 가 유일하게 두 구간 모두
  벤치마크를 넘었다. 복합 점수(+162%, +62%)는 둘 다 후반에만 넘는다
- 기여 상위 3~5종목을 빼면 **모든 전략이 마이너스**가 된다

### 주의 — 이 숫자로 규칙을 바꾸지 않는다

게이트가 해로워 보이고 수익성 부문 단독이 제일 좋아 보인다. 그러나

- 전부 **인샘플**이다. 게이트 임계값·가중치를 이 기간으로 골랐다
- 신호 10개 이상을 나란히 비교한 결과라 **다중검정 보정**을 하면 유의성이 사라진다
  (수익성 부문 t=1.81, p=0.070이 최고값이다)
- 보유종목 수에 민감하다 — 수익성 부문은 top3 +1,172%, top5 +470%, top20 +211%
- 2023~2026 유니버스 구멍이 아직 절반 남아 있다 (§6)

`_성과추적/` 표본이 12개월 쌓이기 전에는 순위를 근거로 규칙을 바꾸지 않는다.

## 5. 재발 방지

이 세 구멍의 공통점은 **아무도 확인하지 않아서 오래 남았다**는 것이다.
시세 결손 때 `btdata.check_coverage()`를 만든 것과 같은 이유로 가드를 더 달았다.

| 무엇 | 어디 |
|---|---|
| 재무 신선도 — 18개월 넘게 묵은 재무로 채점되는 행의 비율 | `btdata.check_staleness()` (매 백테스트) |
| 패널에 재무 공시일 기록 — 없으면 묵었는지 알 수가 없다 | `panel.cohort()`의 `rcept_dt` · `fin_period` |
| 스냅샷 로딩 단일화 — 소비자 5곳이 파일명을 각자 적고 있었다 | `universe.load_snapshots()` · `included_tickers()` |
| 트랙·스냅샷 저장소를 **덮어쓰지 않고 합치기** | `01_build_universe.py` · `02_assign_tracks.py` |
| 전 종목 조회의 빈 응답을 캐시에 남기지 않기 | `krx._cached(cache_empty=False)` |
| 데이터 수정 전후를 같은 규칙으로 비교 | `scripts/27_compare_rebuild.py` |

스냅샷 로딩 단일화가 특히 중요하다. 소비자가 `"universe_history_2018_2022"`를
직접 적어두고 있었기 때문에, **새 스냅샷을 만들어도 백테스트가 보지 않는** 구조였다.

빈 캐시 문제는 이미 피해를 냈다. `names_KOSPI_20201120.parquet`이 빈 채로 캐시돼
2020-11 스냅샷이 계속 실패하고 있었다. 삭제하고 나니 바로 복구됐다.

## 6. 남은 것 — KRX IP 차단

스냅샷 6개(2020-11-20 · 2025-08-20 · 2025-11-20 · 2026-04-05 · 2026-05-20 ·
2026-08-20)와 **신규 40종목의 시세**가 KRX 차단으로 막혔다.
시세가 없으면 그 40종목은 패널에 못 들어간다 — 이번 수정에 아직 반영되지 않았다.

차단 문구:

> KDM 이용 제한 안내 — 자동화 수단을 통한 비정상 대량 조회가 감지되어 해당 IP의
> 접속이 일시적으로 제한되었습니다 … 해당 IP는 **탐지일로부터 1일간** 접속이 제한되며

**그날 KRX 호출은 190회뿐이었다.** 당시 하루 소프트 한도 800회의 4분의 1이다.
0.35초 간격으로 **90초 동안 162회**를 몰아친 것이 걸렸다.
하루 총량으로 안전을 판단하면 안 된다 — **순간 속도가 기준이다.**

차단을 키운 구조도 있었다. pykrx는 요청이 실패하면 **로그인을 다시 시도한다.**
`_cached`의 재시도 3회 × 실패한 스냅샷 6개 = 90초에 로그인 실패 18번.

고친 것:

```
MIN_INTERVAL      0.35초  →  2.0초
BURST_LIMIT       (없음)  →  300초 창당 100회
DAILY_SOFT_LIMIT  800회   →  400회
차단기            (없음)  →  연속 2회 실패 시 이후 호출을 네트워크 없이 거절
차단 사유 표시     (없음)  →  krx.block_notice()가 안내 페이지 문구를 읽는다
```

이 설정으로 스냅샷 16개(약 290콜)가 약 15분이다. 월 1회 작업에 충분하다.

### 2026-09-27 결정 — pykrx 웹 수집을 멈추고 공식 Open API로 옮긴다

차단 안내문의 뒷부분이 결정적이었다.

> 접속 제한 해제 후에는 정상적으로 이용하실 수 있습니다.
> **다만 자동화 수단을 통한 데이터 수집은 제한되며** …

KRX는 빠르게 긁는 것만이 아니라 **웹사이트를 자동으로 긁는 것 자체**를
이용약관(제10조 제2호)으로 제한한다. pykrx가 정확히 그 방식이다 — 개인 KRX
아이디로 로그인한 세션으로 data.krx.co.kr을 긁는다. 위에서 속도를 늦춘 것은
**걸릴 확률을 낮췄을 뿐 약관 문제를 풀지 않는다.** 한경컨센서스·네이버 뉴스를
robots.txt 때문에 공식 API로 옮긴 것과 같은 판단으로, 시세도 공식 창구로 옮긴다.

`src/krx.py`의 **`SCRAPING_ALLOWED = False`**. 캐시에 있는 데이터(시세 96만 행,
스냅샷 30개)는 그대로 쓰고, 캐시에 없는 요청은 네트워크에 나가지 않고 즉시 거절한다.
pykrx 임포트도 막는다 — 임포트가 곧 로그인이다. 소켓을 가로채 검증했다: 연결 시도 0회.

| | pykrx (중단) | **KRX 공식 Open API** |
|---|---|---|
| 허용 여부 | 약관상 제한 | 공식 허용 |
| 인증 | 개인 아이디 로그인 | 발급받은 API 키 |
| 한도 | 우리가 추정 | 인증키당 하루 10,000회 |
| 과거 데이터 | 2017~ | 2010~ |
| 수정주가 | 적용 | **미적용 — 보정 필요** |

신청 절차 (사용자): openapi.krx.co.kr 가입 → 인증키 발급 → **'서비스 이용'에서
유가증권·코스닥 일별매매정보를 각각 신청하고 승인 대기.** 두 번째 단계를 빠뜨리면
키가 멀쩡해도 401이 난다. 키는 `주식시장/.env`의 `KRX_OPENAPI_KEY`.

### 같이 찾은 것 — 성과추적 원장이 조용히 망가질 뻔했다

`run_monthly.py`에 **가격을 받는 단계가 없다.** `prices_daily`가 2026-09-04에 멈춰
있었고, `track.close_at()`은 "기준일 이하 마지막 종가"를 주므로 오류 없이 돌아간다.

```
9/12 기록 진입가    9/4 종가 (이미 8일 묵음)
10월 정산 청산가    9/4 종가 (가격을 안 받으면)
→ 모든 수익률 0.00%로 영구 기록 — 정산된 행은 다시 건드리지 않는다
```

`track.check_fresh()`를 넣어 **가격이 기준일보다 7일 넘게 묵으면 기록·정산을
거부**하게 했다. 오늘 날짜로 돌려 확인했다 — 23일 묵은 가격을 감지해 멈췄고,
원장은 바이트 단위로 그대로다. **멈추게만 했을 뿐 고친 것은 아니다.**
